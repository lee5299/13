# 업무 정리 프로그램 — 개발 진행 권고안

2026-10-30 · 계획 문서 검토 및 기술 조사 · 구현 미착수

**권고: 최신 요구사항과 목업을 맞춘 뒤, Windows에서 어려운 동작을 먼저 시험하고, 요청 한 건의 생성부터 완료·복원까지 연결해 개발한다.** 전체 기능 범위는 유지하고 구현 순서를 나눈다.

검토한 문서는 `업무정리_요구사항_최종확인본.md` 전체 25개 절이다. 이 문서는 사용자 최종 승인 대기 상태다. 이번 검토는 승인이나 개발 착수로 간주하지 않으며, 기존 요구사항과 SpecFrame 상태를 변경하지 않았다.

## 1. 현재 준비된 것과 다음에 필요한 것

업무 흐름, 폴더 이름, 상태, 기록 방식, 반복업무, 예상 부담, 검색과 백업의 제품 범위는 충분히 구체적이다. 같은 기능 질문을 처음부터 다시 할 필요는 없다. 루트폴더·주기 시작일·백업 경로 같은 실제 값은 첫 실행 설정에서 받으면 된다.

다음에는 구현 설계와 검증 기준이 필요하다. 특히 아래 사항을 코드 작성 전에 연결해야 한다.

- 업무폴더를 이동하거나 이름을 바꿔도 같은 요청으로 식별하는 방법.
- 텍스트 원본과 구조화된 업무정보의 저장 위치, 검색용 데이터와의 관계.
- 폴더 이동과 상태 저장 중 하나만 성공했을 때의 재시작·재시도 규칙.
- 앱과 외부 메모장에서 동시에 편집했을 때 양쪽 내용을 보존하는 방법.
- 백업에 기록·설정·결과물이 함께 포함되고 실제로 복원되는지 확인하는 방법.

이 항목들은 새로운 제품 기능을 추가하기 위한 질문이 아니라, 이미 요청한 기능을 안전하게 구현하기 위한 설계 작업이다. 기술 선택과 설계는 개발자가 조사해서 제안하고, 요구 변경이 필요한 경우에만 그 영향을 설명한다.

## 2. 권장 순서와 단계별 통과 조건

| 단계 | 진행할 일 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1. 기준 문서 정리 | 최신 규칙에 맞춰 목업의 불일치를 정리하고, 요구사항별 구현 위치·검증 방법을 개발설계서에 연결한다. | 사용자가 전체 요구사항을 최종 확인한다. 기술 제안과 이미 확정한 제품 요구를 구별한다. |
| 2. 기술 검증 | 가상 업무와 별도 시험폴더로 바탕화면 레이어, 큰 기록창, 외부 폴더 이동, 편집 충돌, 백업·복원을 시험한다. | 실제 Windows에서 관찰한 결과로 구현 방법을 고른다. 불가능하거나 불안정한 부분은 구체적인 시연과 대안을 제시한다. |
| 3. 기본 흐름 연결 | 루트 설정 → 새 요청폴더 → 원문/본인 이해·작업기록 편집 → 캡처·결과물 → 수락 → 완료 → 재실행 후 조회를 연결한다. 검색과 초기 백업·복원도 함께 만든다. | 앱 완료와 탐색기 이동이 같은 업무·상태로 반영되고, 재실행해도 기록·연결·최초 요청시각을 보존한다. 실제 사용일수는 묻지 않는다. |
| 4. 판단·재사용 기능 연결 | 이번 주/달 예상 여유, 마감·중요도 정렬, 검토 요청의 수락 가정, 유형별 양식, 유사명 후보, 지난 제출물 복사, 반복 예상과 1년 일정을 연결한다. | 문서의 대표 사례와 반례를 실제 코드에서 확인한다. 예상 요청만으로 폴더를 생성하거나 후보만으로 유형을 확정하지 않는다. |
| 5. 전체 인수·배포 | 완료 기간검색·묶음, 주기 경계, 백업 설정·보존·실패, 절전 복귀, 화면 배율, 설치·실행을 함께 확인한다. | 실제 사용 환경에서 한 업무의 전체 흐름과 복구를 확인하고, 전체 요구사항 대응표에서 빠진 항목이 없다. |

3단계는 최종 제품 범위를 축소한 버전이 아니라 전체 구현의 첫 연결 구간이다. 실제 업무자료를 맡기기 전에 백업과 별도 위치 복원을 먼저 확인한다. 전체 백업 설정과 이력 보존 기능도 최종 범위에 포함한다.

## 3. 먼저 시험할 핵심 동작

**바탕화면 아래층 목록.** 테두리 제거·반투명 표현과, 아이콘 아래에서 클릭 가능한 목록으로 유지되는 동작은 별도로 확인해야 한다. 다른 창 사용, 바탕화면 보기, 앱 재실행, Windows 탐색기 재시작, 절전 복귀와 화면 배율을 시험 대상으로 둔다. 일반적인 창 순서 API가 있다는 사실만으로 이 요구를 만족했다고 판단하지 않는다. Microsoft는 WinUI/AppWindow의 창 관리와 Win32 창 순서를 문서화하지만, 확인한 자료는 이 제품의 아이콘 아래층 동작을 보증하지 않는다. [AppWindow 설명](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windowing-overview), [Win32 창 순서](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)

**큰 작업기록.** 현재 컨셉을 유지하면서 최대화한 실제 앱에서 읽기 편한 글자 크기로 최소 30줄, 통상 30~50줄을 확인한다. 해상도와 배율에 따라 보이는 줄 수를 기록한다. 글자를 지나치게 줄여 목표를 맞추는 방식은 통과로 보지 않는다.

**탐색기 이동과 되돌리기.** 완료 버튼과 외부 이동, 완료폴더에서 원래 영역으로 복귀, 앱 종료 중 이동, 같은 동작 반복, 이동 중 실패를 시험한다. 실시간 감지만 믿지 않고 시작·재연결·감지 오류 후 실제 폴더 상태를 대조하는 설계를 권한다. .NET의 FileSystemWatcher는 이벤트 중복과 버퍼 초과 시 누락 가능성이 문서화되어 있다. [Microsoft 문서](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher?view=net-10.0)

**저장·복원.** 앱의 미저장 편집과 외부 파일 변경을 함께 보존하고, 백업에서 요청 한 건을 별도 위치로 복원해 텍스트·결과물·캡처·설정 연결을 확인한다. 복사 성공이나 백업 파일 존재만으로 복구 성공을 판단하지 않는다. 처리시간은 실제 파일 수·용량·장치로 측정한다.

## 4. 구현 방식 권고와 대안

우선 검토할 조합은 **C# 기반 Windows 데스크톱 앱 + 작업폴더의 텍스트/실제 파일 + 로컬 SQLite 색인**이다. 인터넷 연결이나 서버 없이 실행되도록 설계한다. 기록의 원본은 작업폴더에 두고, 첨부 문서는 사용자가 선택한 외부 프로그램으로 연다. SQLite는 검색·목록 조회에 쓰되, 무엇이 원본인지와 색인을 다시 만드는 범위를 먼저 정한다. 기록을 두 군데에서 독립적으로 수정하는 구조는 피한다. 이는 구현 제안이며 아직 채택된 명세가 아니다. [Microsoft.Data.Sqlite 개요](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/)

| UI 후보 | 이번 계획과의 연결 | 선택 조건·남은 확인 |
| --- | --- | --- |
| WinUI 3 + Windows App SDK | Windows 전용 창·컨트롤·다중 창의 첫 검토 후보. Microsoft가 새 Windows 앱에 권장하고, 전용 개발 스킬도 발견했다. | 개발환경과 배포 의존성을 확인하고, 특별한 바탕화면 동작과 반투명을 직접 시험한 뒤 채택한다. 스킬이 있다는 이유만으로 결정하지 않는다. |
| WPF | 테두리 없는 투명 창을 공식적으로 구성할 수 있는 비교 후보. 작업 상세창·텍스트 중심 UI와 함께 시험할 수 있다. | 투명 창 지원이 아이콘 아래층 동작의 증거는 아니다. WinUI와 같은 기준으로 실제 요구 충족과 유지보수 부담을 비교한다. |
| Tauri | HTML/CSS를 사용하는 로컬 데스크톱 앱 후보이므로 기존 목업을 화면 자산으로 활용할 가능성이 있다. | 파일 처리·권한·창 동작을 실제 앱 코드로 연결해야 한다. HTML 목업이 있다는 사실만으로 전체 구현이 쉽거나 빠르다고 단정하지 않는다. |

근거: [Microsoft WinUI 3 안내](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/), [WPF 창·투명도 안내](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/windows/), [Tauri 공식 소개](https://v2.tauri.app/start/). 이는 문서상 기능 비교다. 같은 시제품을 만들어 성능이나 개발시간을 비교한 결과는 아니다. 정확한 SDK·패키지 버전은 실제 환경을 확인하고 지원되는 조합으로 고정한다.

이번 간단한 환경 확인에서는 PATH의 dotnet 명령을 찾지 못했고, 기본 설치 경로에서 SDK 2.1.526 폴더를 확인했다. 다른 위치의 개발환경까지 조사한 결과는 아니므로 “개발 도구가 전혀 없다”고 단정하지 않는다. 현대적인 Windows 앱을 빌드할 준비가 끝났다는 근거도 없다. 실제 개발 전에 SDK·Windows SDK·빌드 도구를 확인해야 한다.

백업은 앱의 설정·상태표시·복원 화면과, 실제 자료 보관 엔진을 나누어 검토한다. 기존 엔진 후보로 restic 문서 0.19.1에서 로컬 저장소, 시점별 복원, 파일 선택 복원과 보존 정책을 확인했다. 다만 암호가 필수이며 암호 분실 시 복구할 수 없고, 복원의 기본 덮어쓰기 동작을 앱에서 보호해야 한다. 앱에 연결한 시험은 하지 않았다. 따라서 지금 필수 도구로 확정하지 않고, 암호 보관·이전 PC 고장 후 복구·부분 실패 표시·배포를 검증한 뒤 자체 이력 보관 방식과 비교한다. 어느 방식을 고르든 별도 위치 복원과 기존 원본 보호가 필요하다. [로컬 저장소·암호](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), [선택 복원·덮어쓰기](https://restic.readthedocs.io/en/stable/050_restore.html), [보존 정책](https://restic.readthedocs.io/en/stable/060_forget.html)

## 5. 추천 스킬과 연결 방식

스킬은 개발을 수행하는 AI의 작업 지침이다. 완성된 업무 프로그램을 실행할 때 사용자가 이 스킬들을 별도로 실행해야 하는 구조로 만들지 않는다.

| 스킬 | 맡길 역할·산출물 | 적용 조건과 한계 |
| --- | --- | --- |
| SpecFrame — 설치됨 | 요구사항의 확정/제안/미검증 상태를 보존하고 최종 승인된 개발 기준 문서를 제공한다. | 현재 승인은 대기 중. 이번 조언을 승인으로 바꾸지 않는다. 구현 기술을 대신 결정하는 도구로 쓰지 않는다. |
| SynFrame — 설치됨 | 기술 선택, 부족한 지식, 후보 조합과 검증 근거를 관리하는 용도. | 이번 응답에서는 전체 필수 계약·상태·Review·Commit 절차를 완료하지 못했다. 아래 처리 범위 설명을 따른다. |
| winui-app — 추가 설치 후보 | WinUI 3를 선택할 경우 프로젝트 구성, C#/XAML 화면, 창 관리, 빌드와 실제 실행 확인에 활용한다. | WinUI 경로에 맞는 스킬이다. WPF/Tauri를 선택하면 필수 스킬로 지정하지 않는다. 요구사항을 입력으로 실제 프로젝트를 만들고, 실행된 창과 검증 결과를 다음 검토에 넘긴다. |
| computer-use — 사용 가능 | 실행된 Windows 앱에서 클릭·키보드·창 크기 조절·화면 확인을 수행해 기록 영역과 실제 흐름을 검증한다. | UI 관찰만으로 파일 보존·계산·복원 정확성 전체를 입증하지 않는다. 파일/상태 확인과 계산 테스트를 함께 사용한다. |
| skill-installer — 사용 가능 | 채택한 외부 개발 스킬을 지정된 경로에 설치하는 데 사용한다. | 설치만으로 개발환경이나 기능이 완성되지 않는다. 이번 응답에서는 추가 설치를 하지 않았다. |

추가 후보인 **winui-app**은 이름만 확인한 것이 아니라 실제 SKILL.md와 창 관리 참고자료를 읽었다. Windows 앱 구성·빌드·실행 검증을 다루며 환경 설정 흐름에는 개발자 모드와 Visual Studio/Windows 구성요소 설치·업데이트가 포함된다. 따라서 단순한 문서 검토 중 그 설정을 자동 실행하지 않는다. [스킬 원문](https://github.com/openai/skills/blob/main/skills/.curated/winui-app/SKILL.md), [창 관리 참고자료](https://raw.githubusercontent.com/openai/skills/main/skills/.curated/winui-app/references/shell-navigation-and-windowing.md)

기존 디자인은 개발의 기준으로 유지한다. imagegen/visualize는 새로운 디자인 비교가 실제로 필요해졌을 때의 보조 도구로 두며, 현재 단계의 필수 추가 작업으로 잡지 않는다. Sites는 웹사이트 제작·게시용 스킬이므로 이번 Windows 프로그램의 중심 개발 도구로 추천하지 않는다. 이것이 HTML 기반 로컬 앱 자체가 불가능하다는 뜻은 아니다.

## 6. 문서와 목업에서 바로 맞출 부분

- 별도 착수 예정 날짜 칸을 없애고, 예상 작업일수를 완성까지 필요한 작업량으로 표현한다.
- 목록 복사 기능을 제거하고, 요청 원문과 본인 이해를 나눈다.
- 검토중 요청과 수락된 업무를 구별하고, 이번 주/달 예상 여유를 표시한다.
- 유사명 클릭은 작업명/유형 후보를 채우는 동작으로 하고, 폴더 생성과 반복 등록은 별도 확인된 동작으로 둔다.
- 선택한 양식만 복사한다. 현재 목업의 작업기록.txt 해제 불가 동작을 확정 요구로 남기지 않는다.
- 완료 창의 기간·묶음 날짜 기준과 요청등록시간 정렬을 구분한다. 개발설계에서 “묶음의 기준은 선택한 날짜, 묶음 안의 행은 최초 요청등록 최신순”처럼 두 규칙이 공존하는 방식을 명시하는 것을 제안한다. 이는 해석 제안이며 기존 문서를 변경하지 않았다.

업무부담 수치는 진행률을 받지 않는 한 실제 잔여량과 같을 수 없다. 현재 계획대로 미완료 업무의 등록 예상량을 보수적으로 사용하고, 완료 후 그 부담을 제외한다. 예를 들어 5일 예상 업무가 완료되었다고 해서 별도의 “2일 환급”을 누적하지 않는다. 오늘을 포함한 남은 평일 능력에서 다시 계산한다. 이 한계를 화면의 “예상” 표현과 검증 사례에 유지해야 한다.
